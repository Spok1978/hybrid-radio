## Что делает проверочная программа

Три вещи, которых нельзя узнать по бумаге:

1. **Ревизия кристалла.** Свежие ESP-IDF по умолчанию поддерживают только
   ревизии от 3.1; для 1.x нужны особые настройки SDK. Пока неизвестно,
   какая ревизия на нашем экземпляре.
2. **Фактический объём PSRAM.** В неё лягут буфер потока и рабочая память
   декодера. Заявлено 32 МБ.
3. **Опрос шины I²C.** Кто реально отвечает: штатные GT911, ES8311, ES7210
   и — когда подключим — тюнер RDA5807M и расширитель портов. Заодно
   подтвердит, что подтяжек своих не надо.

## Порядок запуска

Инструментарий ставится **не GUI-установщиком**: он интерактивный.
Вместо этого клонируется ESP-ADF со своим закреплённым ESP-IDF
и запускается его скрипт установки.

```bash
git clone -b release/v2.x --recursive https://github.com/espressif/esp-adf.git C:/Users/telen/esp/esp-adf
```

Затем, из папки `esp-adf`, установка инструментов под нашу цель:

```bash
./install.ps1 esp32p4
```

Дальше в каждой новой оболочке подтягивается окружение, и уже потом сборка:

```bash
./export.ps1
```

```bash
idf.py set-target esp32p4 build
```

## Конфигурация — угадывать больше не нужно

Вчера этот раздел был списком «выставить руками и проверить», потому что
имён символов Kconfig я не знала. Теперь знаю: ESP-ADF склонирован, и в нём
лежит готовый набор под нашу цель —
`examples/player/pipeline_http_mp3/sdkconfig.defaults.esp32p4`.
Всё, что относится к кристаллу, перенесено в `sdkconfig.defaults`
с указанием источника.

Что оттуда подтвердилось:

| Ключ | Было | Стало |
|---|---|---|
| `CONFIG_ESP_WIFI_REMOTE_LIBRARY_HOSTED=y` | по поисковой выдаче, помечен как непроверенный | **подтверждён**, рядом стоит `CONFIG_SLAVE_IDF_TARGET_ESP32C6=y` |
| `CONFIG_ESP32P4_SELECTS_REV_LESS_V3` | «понадобится, если ревизия 1.x» | **существует и пишется именно так**, у ADF стоит `=n` |
| PSRAM | «имена символов отличаются, выяснить» | `CONFIG_SPIRAM=y`, `CONFIG_SPIRAM_SPEED_200M=y`, `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y` |

Осталось выставить только `CONFIG_LVGL_PORT_ENABLE_PPA` — этого символа
ещё нет, он появится вместе с портом LVGL.

Две строки из набора ADF **сознательно не взяты**, обе относятся к чужой
плате: выбор звукового HAL под Espressif EV-Board и увод консоли
на USB-Serial/JTAG. Подробности — в комментариях внутри `sdkconfig.defaults`.

## Конфликт версий, найденный до сборки

Манифест примера ADF требует `esp_hosted` **^2.6.4** при IDF 5.4 и выше.
Waveshare для своей платы указывает **1.4.\***. Диапазоны не пересекаются.

Причина: Waveshare отвечает, какой хост говорит с образом прошивки C6
на их плате, ADF — с чем проверялся он сам. Собрать по версиям ADF —
соберётся, но может не заговорить с сопроцессором.

**Поэтому порядок первой сборки изменён.** Сначала поднимаем плату и сеть
по версиям Waveshare, без ADF. Убеждаемся, что сопроцессор отвечает.
И только потом добавляем ADF — тогда будет понятно, что именно сломалось,
если сломается. Разбор и три пути выхода —
[docs/26](../docs/26-firmware-spec.md), §2.4.

## Первая настоящая проверка — не эта

Проверочная программа доказывает только что инструментарий работает.
Главная проверка другая: **собрать пример `pipeline_http_mp3` из ESP-ADF
под нашу плату и получить звук.** Она подтверждает или обесценивает выбор
ESP-ADF как звукового тракта, потому что ADF писался под чипы с собственным
радио, а у нас Wi-Fi через сопроцессор.

Два условия совместимости, которые надо соблюсти при этой сборке:

- держать версии host и slave согласованными — и здесь как раз обнаружился
  конфликт, см. раздел выше;
- про `esp-extconn`: предупреждение из сторонних источников к нам
  **не относится**, такого компонента в ADF нет вовсе (проверено
  2026-08-27 по склонированному дереву).

## Чего в каркасе намеренно нет

Логики приёмника, интерфейса, работы с тюнером и хранения станций.
Писать это вслепую, до первой успешной сборки, значит накопить непроверенный
код — а он потом чинится дольше, чем пишется с нуля по работающему каркасу.
