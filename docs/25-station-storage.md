# 25. Хранение списка радиостанций: постановка задачи

Написано 2026-08-26 как **самостоятельная постановка вопроса Q13**. Документ
читается без остального проекта — его можно показать кому угодно целиком.

## 1. Что за прибор

Настольный радиоприёмник с двумя режимами: эфир (УКВ OIRT 65,8–74 МГц и
FM CCIR 87,5–108 МГц через тюнер RDA5807M по I²C) и интернет-радио.

- Платформа: **ESP32-P4**, плата Waveshare ESP32-P4-WIFI6-Touch-LCD-5,
  Wi-Fi через сопроцессор ESP32-C6, карта TF, экран DSI, кодек ES8311.
- Прошивка-основа: **`schreibfaul1/ESP32-MiniWebRadio`**, проект ESP-IDF.
  Она умеет интернет-радио, поиск через Radio Browser, веб-интерфейс.
  Эфирного режима в ней нет — тюнер и всё, что с ним связано, пишем мы.
- Каталог станций: Radio Browser используется **только как поисковик**.
  Найденное складывается в прибор, дальше он играет из своего списка.

## 2. Что нужно хранить

**Про интернет-станцию:**

| Поле | Зачем |
|---|---|
| `name` | показать на экране |
| `url` | собственно поток |
| `country` | группировка и фильтр в списке |
| `stationuuid` | идентификатор станции в Radio Browser: по нему отмечается клик и **подтягивается новый URL, когда вещатель его сменил** |
| `codec`, `bitrate` | показать на экране, отсеять заведомо неиграбельное |
| `last_verified` | когда станцию последний раз проверяли |
| `source` | найдено в каталоге / вбито руками / импортировано из `.m3u` |

**Пресеты.** Восемь ячеек быстрого доступа, кнопки 1–8. Ячейка хранит
станцию **любого из двух режимов**: либо эфирную частоту, либо интернет-поток.
Нажатие пресета само переводит прибор в нужный режим. То есть запись пресета
несёт тип:

```json
{"n": 1, "type": "fm",  "freq_khz": 102500, "band": "ccir", "name": "Retro FM"}
{"n": 2, "type": "net", "url": "http://...", "name": "Radio Record"}
```

## 3. Что даёт прошивка сейчас

Список станций лежит на карте в файле **`/stations.json`**. Одна станция —
массив из четырёх строк: признак избранного, код страны, название, URL.

```json
["*", "DE", "0N 70s", "http://0n-70s.radionetz.de:8000/0n-70s.mp3"]
```

Места ни для одного из остальных полей нет, и **места для эфирных пресетов
нет тем более** — прошивка про УКВ/FM ничего не знает.

## 4. Почему нельзя просто дописать пятое поле

Разбор по исходникам ветки master, файл `src/mwr_src/function.hpp`, метод
`stationManagement::updateStationsList()`:

```cpp
if (c == '\"') {
    int pos = file.readBytesUntil('\"', buff, 1024);
    buff[pos] = 0;
    if (item == 0) { m_stations.fav.push_back(buff[0]); m_staCnt++; }
    if (item == 1) { m_stations.country.push_back(x_ps_strdup(buff)); }
    if (item == 2) { m_stations.name.push_back(x_ps_strdup(buff)); }
    if (item == 3) { m_stations.url.push_back(x_ps_strdup(buff)); }
    item++;
    if (item > 3) item = 0;
```

**Это не разбор JSON.** Парсер идёт по файлу и подряд ловит всё, что стоит
в кавычках. Скобки, запятые и переводы строк он пропускает. Счётчик полей
`item` крутится по кругу 0→1→2→3→0 и **на границе записи не сбрасывается** —
ни `]`, ни `[` его не трогают.

Отсюда главное следствие: **пятая строка в записи не игнорируется.** Она
попадает в поле `fav` следующей станции, и с этого места весь остаток файла
разъезжается на одно поле. Один лишний элемент ломает весь список ниже себя.

То есть формат — не «четыре поля, дальше можно дописывать». Это «ровно четыре
кавычечных строки на запись, во всём файле, иначе всё, что ниже, съезжает».

Из того же кода следует ещё одно ограничение: экранированная кавычка внутри
названия станции тоже посчитается границей поля, потому что чтение идёт
через `readBytesUntil('\"', ...)`. Названия с кавычками ломают файл.

## 5. Что ещё не выяснено

**Пишет ли прошивка `/stations.json` сама.** В `function.hpp` кода записи
не нашлось — только чтение. Но README проекта говорит, что станции правятся
через встроенный веб-интерфейс, а его код лежит в других файлах
(`index.h`, `index.js.h`), которые не смотрели.

Это важно, потому что определяет судьбу любого решения:

- если прошивка перезаписывает файл — она выбросит всё, что мы туда добавили;
- если она при этом ещё и меняет порядок записей — то и внешний файл-спутник
  нельзя привязывать к номеру строки, только к URL.

## 6. Варианты

| № | Вариант | Суть |
|---|---|---|
| 1 | **Файл-спутник** | `/stations.json` не трогаем вообще. Рядом кладём свой файл: банк пресетов и дополнительные поля станций, привязанные к URL |
| 2 | **Форк модуля станций** | свой формат целиком, парсер переписываем под себя |
| 3 | Пятое поле в записи | по §4 не работает без правки парсера, а с правкой это уже вариант 2 |
| 4 | Спрятать данные в существующем поле | дописать в `country` или в хвост `name` |
| 5 | Отказаться от лишних полей | живём тремя, теряем `stationuuid` |
| 6 | Прошивка только как звуковой движок | список ведём полностью своим кодом; крайний случай варианта 2 |

Разбор:

**Вариант 1.** Апстрим обновляется без боли, веб-интерфейс прошивки
продолжает работать как есть. Минус: два файла надо держать согласованными,
и ключом может быть только URL, потому что порядок записей нам не
подконтролен.

**Вариант 2.** Всё в одном месте, никаких согласований. Минус: обновления
апстрима переносим руками; если веб-интерфейс пишет файл, его надо править
вместе с парсером.

**Вариант 4** ломается при первой же правке через веб-интерфейс, а `name`
ещё и показывается на экране. **Вариант 5** не закрывает задачу: пресеты
всё равно негде хранить.

## 7. Наблюдение, из-за которого задача проще, чем кажется

Эфирные пресеты **в любом случае** не помещаются в `/stations.json` —
у формата нет для них места, и добавить его нельзя по §4. Значит свой файл
понадобится при любом раскладе, кроме форка.

А раз свой файл всё равно есть, дополнительные поля станций почти ничего
не стоит положить туда же. Две проблемы сводятся к одной, и вариант 1
оказывается дешёвым.

## 8. Что хочется спросить у стороннего мнения

1. Нет ли способа хранить `stationuuid` и остальное так, чтобы не заводить
   второй файл и не форкать парсер?
2. Если файл-спутник — чем связывать записи, кроме URL? URL меняется, а именно
   ради отслеживания его смены `stationuuid` и нужен: получается замкнутый круг.
3. Насколько разумно вообще опираться на прошивку с таким парсером, или
   правильнее сразу брать её как звуковой движок и вести список самим?
4. Есть ли у кого-то опыт с этой прошивкой в части записи `/stations.json`
   из веб-интерфейса — переписывает ли она файл целиком?
