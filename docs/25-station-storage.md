# 25. Хранение списка радиостанций: постановка задачи

Написано 2026-08-26 как **самостоятельная постановка вопроса Q13**. Документ
читается без остального проекта — его можно показать кому угодно целиком.

## 1. Что за прибор

Настольный радиоприёмник с двумя режимами: эфир (УКВ OIRT 65,8–74 МГц и
FM CCIR 87,5–108 МГц через тюнер RDA5807M по I²C) и интернет-радио.

- Платформа: **ESP32-P4**, плата Waveshare ESP32-P4-WIFI6-Touch-LCD-5,
  Wi-Fi через сопроцессор ESP32-C6, карта TF, экран DSI, кодек ES8311.
- Прошивка-основа: **`schreibfaul1/ESP32-MiniWebRadio`**, проект ESP-IDF.
  Она умеет интернет-радио, поиск через Radio Browser, веб-интерфейс.
  Эфирного режима в ней нет — тюнер и всё, что с ним связано, пишем мы.
- Каталог станций: Radio Browser используется **только как поисковик**.
  Найденное складывается в прибор, дальше он играет из своего списка.

## 2. Что нужно хранить

**Про интернет-станцию:**

| Поле | Зачем |
|---|---|
| `name` | показать на экране |
| `url` | собственно поток |
| `country` | группировка и фильтр в списке |
| `stationuuid` | идентификатор станции в Radio Browser: по нему отмечается клик и **подтягивается новый URL, когда вещатель его сменил** |
| `codec`, `bitrate` | показать на экране, отсеять заведомо неиграбельное |
| `last_verified` | когда станцию последний раз проверяли |
| `source` | найдено в каталоге / вбито руками / импортировано из `.m3u` |

**Пресеты.** Восемь ячеек быстрого доступа, кнопки 1–8. Ячейка хранит
станцию **любого из двух режимов**: либо эфирную частоту, либо интернет-поток.
Нажатие пресета само переводит прибор в нужный режим. То есть запись пресета
несёт тип:

```json
{"n": 1, "type": "fm",  "freq_khz": 102500, "band": "ccir", "name": "Retro FM"}
{"n": 2, "type": "net", "url": "http://...", "name": "Radio Record"}
```

## 3. Что даёт прошивка сейчас

Список станций лежит на карте в файле **`/stations.json`**. Одна станция —
массив из четырёх строк: признак избранного, код страны, название, URL.

```json
["*", "DE", "0N 70s", "http://0n-70s.radionetz.de:8000/0n-70s.mp3"]
```

Места ни для одного из остальных полей нет, и **места для эфирных пресетов
нет тем более** — прошивка про УКВ/FM ничего не знает.

## 4. Почему нельзя просто дописать пятое поле

Разбор по исходникам ветки master, файл `src/mwr_src/function.hpp`, метод
`stationManagement::updateStationsList()`:

```cpp
if (c == '\"') {
    int pos = file.readBytesUntil('\"', buff, 1024);
    buff[pos] = 0;
    if (item == 0) { m_stations.fav.push_back(buff[0]); m_staCnt++; }
    if (item == 1) { m_stations.country.push_back(x_ps_strdup(buff)); }
    if (item == 2) { m_stations.name.push_back(x_ps_strdup(buff)); }
    if (item == 3) { m_stations.url.push_back(x_ps_strdup(buff)); }
    item++;
    if (item > 3) item = 0;
```

**Это не разбор JSON.** Парсер идёт по файлу и подряд ловит всё, что стоит
в кавычках. Скобки, запятые и переводы строк он пропускает. Счётчик полей
`item` крутится по кругу 0→1→2→3→0 и **на границе записи не сбрасывается** —
ни `]`, ни `[` его не трогают.

Отсюда главное следствие: **пятая строка в записи не игнорируется.** Она
попадает в поле `fav` следующей станции, и с этого места весь остаток файла
разъезжается на одно поле. Один лишний элемент ломает весь список ниже себя.

То есть формат — не «четыре поля, дальше можно дописывать». Это «ровно четыре
кавычечных строки на запись, во всём файле, иначе всё, что ниже, съезжает».

Из того же кода следует ещё одно ограничение: экранированная кавычка внутри
названия станции тоже посчитается границей поля, потому что чтение идёт
через `readBytesUntil('\"', ...)`. Названия с кавычками ломают файл.

## 5. Что ещё не выяснено

**Пишет ли прошивка `/stations.json` сама.** В `function.hpp` кода записи
не нашлось — только чтение. Но README проекта говорит, что станции правятся
через встроенный веб-интерфейс, а его код лежит в других файлах
(`index.h`, `index.js.h`), которые не смотрели.

Это важно, потому что определяет судьбу любого решения:

- если прошивка перезаписывает файл — она выбросит всё, что мы туда добавили;
- если она при этом ещё и меняет порядок записей — то и внешний файл-спутник
  нельзя привязывать к номеру строки, только к URL.

## 6. Варианты

| № | Вариант | Суть |
|---|---|---|
| 1 | **Файл-спутник** | `/stations.json` не трогаем вообще. Рядом кладём свой файл: банк пресетов и дополнительные поля станций, привязанные к URL |
| 2 | **Форк модуля станций** | свой формат целиком, парсер переписываем под себя |
| 3 | Пятое поле в записи | по §4 не работает без правки парсера, а с правкой это уже вариант 2 |
| 4 | Спрятать данные в существующем поле | дописать в `country` или в хвост `name` |
| 5 | Отказаться от лишних полей | живём тремя, теряем `stationuuid` |
| 6 | Прошивка только как звуковой движок | список ведём полностью своим кодом; крайний случай варианта 2 |

Разбор:

**Вариант 1.** Апстрим обновляется без боли, веб-интерфейс прошивки
продолжает работать как есть. Минус: два файла надо держать согласованными,
и ключом может быть только URL, потому что порядок записей нам не
подконтролен.

**Вариант 2.** Всё в одном месте, никаких согласований. Минус: обновления
апстрима переносим руками; если веб-интерфейс пишет файл, его надо править
вместе с парсером.

**Вариант 4** ломается при первой же правке через веб-интерфейс, а `name`
ещё и показывается на экране. **Вариант 5** не закрывает задачу: пресеты
всё равно негде хранить.

## 7. Наблюдение, из-за которого задача проще, чем кажется

Эфирные пресеты **в любом случае** не помещаются в `/stations.json` —
у формата нет для них места, и добавить его нельзя по §4. Значит свой файл
понадобится при любом раскладе, кроме форка.

А раз свой файл всё равно есть, дополнительные поля станций почти ничего
не стоит положить туда же. Две проблемы сводятся к одной, и вариант 1
оказывается дешёвым.

## 8. Что хочется спросить у стороннего мнения

1. Нет ли способа хранить `stationuuid` и остальное так, чтобы не заводить
   второй файл и не форкать парсер?
2. Если файл-спутник — чем связывать записи, кроме URL? URL меняется, а именно
   ради отслеживания его смены `stationuuid` и нужен: получается замкнутый круг.
3. Насколько разумно вообще опираться на прошивку с таким парсером, или
   правильнее сразу брать её как звуковой движок и вести список самим?
4. Есть ли у кого-то опыт с этой прошивкой в части записи `/stations.json`
   из веб-интерфейса — переписывает ли она файл целиком?

## 9. Решение (2026-08-26)

Получены два сторонних разбора. Оба сходятся на варианте 1 и оба против
форка. Но архитектуру предлагают разную, и здесь они не равноценны.

- **Разбор Б** повторяет исходную постановку: `/stations.json` — мастер,
  наш файл догоняет его по ключу-URL. Замкнутый круг из §8 остаётся
  неразрешённым, а перезапись файла подтверждается ссылкой на release notes.
- **Разбор А** переворачивает связь: **мастер — наш файл, `/stations.json` —
  производная проекция**, которую наш код перегенерирует. Перезапись
  подтверждена не по release notes, а по коду веб-интерфейса.

**Принят разбор А.** Ключевое: связь нужна только в одну сторону,
«мастер → проекция», и она тривиальна. Привязывать записи не к чему,
и вопрос 2 из §8 снимается не ответом, а исчезновением.

### Что проверено самостоятельно

Утверждения разбора А проверены по исходникам ветки master 2026-08-26,
потому что на них держится вся схема.

| Утверждение | Результат |
|---|---|
| Веб-интерфейс переписывает файл целиком | **подтверждено.** В `index.h` четыре места — правка ячейки, вставка строки, удаление строки, загрузка файла — и все вызывают `saveJsonFileToSD("/stations.json", JSON.stringify(tableData, 0, 2))` |
| Предел 999 станций | **подтверждено, и он в парсере:** `if (m_staCnt > 999) break;`. Раньше 999 брались из README и как факт не принимались — теперь принимаются |
| Поле `fav` не свободно под наши данные | **подтверждено.** JS проверяет `const validValues = ['*', '1', '2', '3'];`, невалидное значение затирается в пустое |

**И одно, чего не проверил ни один разбор, хотя на нём держится всё:**
безопасно ли звать `updateStationsList()` повторно. Если бы метод только
дописывал в векторы, перегенерация удваивала бы список при каждом вызове.

Проверено — безопасно:

```cpp
void updateStationsList() {
    clearStations();
    uint8_t item = 0;
    m_staCnt = 0;
    m_staFavCnt = 0;
```

Метод публичный и чистит состояние перед разбором. Именно это делает схему
«перегенерировали проекцию → перечитали» работоспособной.

### Четыре добавления к разбору А

**1. Импорт не на старте, а перед каждой перегенерацией.** Разбор А
предлагает подбирать правки из веб-интерфейса при загрузке. Этого мало:
веб пишет в любой момент, и наша перегенерация тоже может случиться в любой
момент — правка, сделанная в середине сеанса, будет уничтожена. Поэтому
**перегенерация всегда read-modify-write**: прочитать проекцию, сверить
с мастером, слить, записать. Слепой записи не бывает.

**2. Поле `fav` хранится в мастере.** Это пользовательские данные —
отметки избранного, четыре значения плюс пустое. Живут они только в
проекции, и при перегенерации из мастера были бы стёрты. Значит мастер
обязан их знать.

**3. Политика обрезки до 999.** Мастер может вырасти больше предела
парсера. Проекция обрезается детерминированно: сначала всё избранное,
дальше по времени последнего проигрывания. Что не влезло — остаётся
в мастере и доступно через наш интерфейс.

**4. Проекция одноразовая — и это сужает Q14.** Если `/stations.json`
испортится при обрыве записи, он просто перегенерируется из мастера.
Реальной защиты требует **только файл мастера**, а не оба. Это довод
в пользу схемы, которого нет ни в одном разборе.

Оговорка к совету разбора А «писать оба файла атомарно, tmp + rename»:
это перенос привычки из Linux. Атомарность `rename()` на FATFS в ESP-IDF
не установлена — см. Q14 в [06](06-open-questions.md). Совет верен по
направлению, но гарантией пока не является.

### Итоговая схема

| Файл | Роль |
|---|---|
| `/ipradio.json` | **мастер, единственный источник истины**: банк пресетов (эфир и интернет), все поля станций из §2, поле `fav`, внутренний стабильный ID |
| `/stations.json` | **производная проекция** для прошивки: ровно четыре строки на запись, генерируется нами, перечитывается вызовом `updateStationsList()` |

Смена URL вещателем перестаёт быть проблемой: её инициируем мы сами —
резолв по `stationuuid` в Radio Browser, правка мастера, перегенерация
проекции. Ситуации «URL сменился снаружи, а мы не знаем» не возникает.

Форк не берём. Поверхность, на которую опираемся, крошечная: «ровно четыре
кавычечных строки на запись» и публичный `updateStationsList()`. Парсер
уродлив, но это **плохой стабильный контракт, а не плохое непредсказуемое
поведение** — формулировка разбора А, и она точна. Пересмотр — когда свой
интерфейс разрастётся настолько, что список станций в прошивке всё равно
не показывается; мастер-файл к тому моменту уже будет.

### Принято из разборов дополнительно

- **Санитизация имён.** Кавычки и переводы строк в названии ломают парсер
  (`readBytesUntil('\"', ...)`), а `JSON.stringify` в вебе их экранирует —
  то есть в апстриме такие имена сломаны сквозным образом. Наш генератор
  их вычищает, наш импортёр терпит уже сломанный файл.
- **RDS-имя отдельным полем** от пользовательского `name` — чтобы показывать
  «как в эфире» и «как назвал пользователь» по отдельности.

### Побочное следствие для Q9

Веб-интерфейс отклонялся ([06](06-open-questions.md), Q9) как **второй
интерфейс, который пришлось бы писать**. У MiniWebRadio он уже есть и уже
работает — то есть посылка вопроса Q9 изменилась. Для массового ввода
станций это может оказаться удобнее импорта `.m3u` с флешки. Отдельного
решения не принимаю, но помечаю: Q9 стоит перечитать, когда плата придёт.

## 10. Решение §9 отменено 2026-08-26

В тот же день заказчик уточнил: **прошивка пишется с нуля**, база
`schreibfaul1/ESP32-MiniWebRadio` не используется
([26](26-firmware-spec.md), §3).

Вместе с ней отпадает всё, ради чего затевалась схема «мастер + проекция»:
чужого парсера нет, обходить нечего. Список станций — просто наш файл
`/ipradio.json`, структура §2 реализуется напрямую, без четырёх полей,
без предела в 999 записей и без перегенерации проекции.

**Что из разбора остаётся в силе:**

- структура данных из §2 — она и так была нашей;
- раздельное хранение RDS-имени и пользовательского имени;
- санитизация кавычек и переводов строк в именах — теперь не ради чужого
  парсера, а просто как гигиена;
- атомарная запись с двумя копиями и контрольной суммой — вопрос Q14
  никуда не делся;
- наблюдение, что размер банка пресетов не связан с числом кнопок.

**Что становится историей:** §4 (почему не влезает пятое поле), §5, §6, §7
и вся §9 — они описывают ограничения формата, которого в приборе больше
не будет. Документ сохранён целиком: если когда-нибудь встанет вопрос
совместимости с MiniWebRadio или переноса станций оттуда, разбор пригодится
готовым.
