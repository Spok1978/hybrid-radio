# 14. Программная часть: принятый стек и план работ

Составлено 2026-08-21 по итогам разбора внешних рекомендаций по софту
(тот же источник, что и аудит железа, см. [12](12-audit-response.md)).
Большая часть рекомендаций принята, четыре — с изменениями, одна отложена.

Карта выводов и `config.txt` — в [13-gpio-map.md](13-gpio-map.md), здесь
не дублируются.

## 1. Что пришлось поправить в исходных рекомендациях

### 1.1. Строка экрана в config.txt неверна

Рекомендации предлагают `dtoverlay=vc4-kms-dsi-waveshare-panel,5_0_inchC`.
Такого параметра **не существует** — проверено по списку оверлеев в ветках
ядра rpi-6.6.y, 6.12.y и 6.17.y, разбор в [12](12-audit-response.md), §2.1.
Правильная строка для принятой панели 7″ (C):

```ini
dtoverlay=vc4-kms-dsi-waveshare-panel,7_0_inchC
```

### 1.2. В примере кнопок занят вывод I²S

В предложенном config.txt есть строка `dtoverlay=gpio-key,gpio=19,...`,
а **GPIO19 — это I²S LRCLK**, линия к ЦАП PCM5102A. Причём в примечании
ниже по тексту тех же рекомендаций сказано «не занимайте 18/19/20/21 (I²S)» —
то есть пример противоречит собственному предупреждению. Ориентируемся на
карту выводов из [13](13-gpio-map.md), а не на пример.

### 1.3. Тумблер режима — это уровень, а не нажатие

Тумблер предложено завести через `gpio-key`. Само по себе работает, но есть
подвох: `gpio-key` порождает события «нажал/отпустил», а тумблер — это
**состояние**. После включения прибора никакого события не будет, пока
тумблер не щёлкнут, и режим окажется неизвестен.

Решение: при старте **читать текущий уровень**, а не ждать события —
через `device.active_keys()` в evdev либо чтением линии напрямую. Дальше
уже работать по событиям. Записано как обязательный пункт в §4.

### 1.4. «Включил — играет за 5–10 с» — так не будет

Raspberry Pi 3B+ с SD-карты и образом Lite поднимается до пользовательского
пространства порядка 20–25 с. Пять секунд недостижимы никакой оптимизацией
автозапуска. Цель оставляем прежней и честной: **играет менее чем через
20 с**, и это цель, а не обещание. Приём «звук раньше интерфейса» при этом
полностью принимается — он даёт выигрыш в несколько секунд.

## 2. Архитектура процессов: два, а не три

Рекомендовано три службы: `radio-core`, `radio-ui`, `mpd`. Аргумент —
«падение UI не роняет звук».

**На нашем железе этот аргумент не работает.** Звук переживает падение
интерфейса и без разделения:

- в режиме INET играет **MPD** — отдельный демон, наш процесс ему не нужен;
- в режиме FM звук идёт **аппаратно через тюнер**: RDA5807M после настройки
  играет сам, софт ему нужен только чтобы сменить частоту или громкость.

То есть разделение на два наших процесса покупает изоляцию, которая уже есть,
а платим за неё межпроцессным взаимодействием, вторым юнитом, порядком
запуска и вдвое более сложной отладкой.

**Принято:**

| Служба | Что делает |
|---|---|
| `mpd` | воспроизведение интернет-потоков, штатный юнит |
| `radio` | всё наше: автомат состояний, тюнер, пресеты, база станций, Radio Browser, ввод, интерфейс |

Внутри `radio` ядро отделено от интерфейса **программной границей** —
модуль `core` не знает про pygame, интерфейс не лезет в регистры тюнера.
Когда (и если) понадобится веб-слой, эта граница выносится в локальный
сокет без переписывания ядра. Ровно то, что записано в Q9.

## 3. Хранение данных: JSON, а не SQLite

Рекомендации предлагают SQLite и одновременно требуют писать «через
tmp → fsync → rename с A/B-копиями». **Это несовместимая пара:** атомарная
замена файла работает для обычных файлов, а для SQLite означала бы копирование
всей базы при каждой правке пресета.

Выбираем одно. При наших объёмах — несколько сотен станций и до десятка
пресетов — берём **JSON-файлы с атомарной заменой** из [10](10-shutdown-and-data-safety.md):

- совпадает с уже принятой схемой сохранности данных;
- читается глазами и правится руками через SSH;
- тривиально экспортируется на флешку и обратно.

SQLite вернём, если база разрастётся до тысяч записей — тогда и откажемся от
rename в пользу её собственного журнала (`journal_mode=DELETE`,
`synchronous=FULL`; WAL на разделе, смонтированном `ro`, нежизнеспособен).

**Кэш результатов поиска** по Radio Browser — на разделе данных, но
**одноразовый**: атомарность ему не нужна, битый кэш просто удаляется.
В tmpfs его класть не стоит — прибор выключают питанием, и кэш терялся бы
при каждом включении, ровно тогда, когда он нужен.

Что храним про станцию: `name`, `url`, `codec`, `bitrate`, `country`,
**`stationuuid`**, `last_verified`, `source` (`radio_browser` / `manual` / `m3u`).
UUID нужен для двух вещей — отметить клик в каталоге и подтянуть новый URL,
если вещатель его сменил.

## 4. Принятые решения по узлам

### Тюнер

- Свой модуль `rda5807.py` поверх `smbus2`, **логику портируем с библиотеки
  PU2CLR RDA5807** (MIT), а не выводим регистровую модель из даташита с нуля.
- Порог SEEK — **параметр диапазона**, калибруется на макете отдельно для
  OIRT и FM: в полупустом OIRT высокий порог пропустит слабые станции,
  низкий — остановится на шуме.
- **RDS опрашиваем только в FM.** В OIRT его нет, там пресеты подписываются
  вручную ([02](02-fm-frontend.md)).
- API не завязывать жёстко на «BAND + CHAN»: оставить дорогу «прямой частоте»
  (рег. 07H FREQ_MODE + рег. 08H).

### Громкость — абстракция с двумя реализациями

Лучшая мысль из всех рекомендаций. Громкость регулируется **по-разному**:
в FM — регистром чипа (0–15), в INET — микшером/`setvol` у MPD. Прячем это
за один интерфейс `VolumeBackend`, чтобы ни энкодер, ни интерфейс не знали,
кто сейчас играет. Иначе развилки по режиму расползутся по всему коду.

### Интернет-радио

- **MPD + `python-mpd2`.** Плейлисты `.pls` / `.m3u` / `.m3u8` разворачиваем
  **сами**, в MPD передаём конечный URL — так виден реальный источник ошибки
  и возможен перебор зеркал.
- Подписка на **idle-события** MPD: поток умер → до трёх повторов с
  нарастающей паузой → следующий URL станции → режим OFFLINE.
- **Проверить `mpd --version` на `hls+https`** до написания кода. Если сборка
  окажется без ffmpeg-плагина или капризной — переходим на `mpv`.

### Ввод

- Оверлеи `gpio-key` и `rotary-encoder`, чтение через `python-evdev`
  (принято ранее, [13](13-gpio-map.md)).
- **Длинное и короткое нажатие** — по паре событий down/up с таймстампами
  ядра, порог 500–800 мс.
- **Ускорение энкодера**: события чаще ~100 мс → шаг перестройки ×10.
- **Тумблер: читать уровень при старте** (§1.3).
- На макете сначала `evtest`, потом свой код.

### Интерфейс

- **pygame поверх KMSDRM**, без иксов и браузера. PyQt5 остаётся запасным.
- Перерисовка **по событиям**, а не 60 кадров в секунду; индикатор RSSI —
  таймером 2–4 Гц.
- Шрифт с кириллицей — DejaVu Sans или Noto Sans из репозитория.
- **Гашение подсветки** по таймауту через `/sys/class/backlight` — проверить,
  что драйвер панели этот интерфейс отдаёт.
- В меню «О приборе» — `vcgencmd get_throttled`, версия, состояние Wi-Fi.

### Система и надёжность

- **Raspberry Pi OS Lite, 64-бит, минимум Bookworm.**
- Wi-Fi — **NetworkManager через `nmcli`**, своей обвязки над wpa_supplicant
  не пишем: `nmcli` закрывает R2.1–R2.3 целиком.
- **Аппаратный watchdog**: `dtparam=watchdog=on` (параметр проверен по списку
  оверлеев: «Set to "on" to enable the hardware watchdog») плюс
  `RuntimeWatchdogSec=15` в `/etc/systemd/system.conf`.
- `Restart=always`, `RestartSec=3` у наших служб.
- **Обновления только вручную** из меню: выключить overlayfs → обновиться →
  включить обратно → перезагрузка. Никаких автоматических обновлений.
- **Логи** — journald с ограничением объёма; на read-only корне они и так
  не доживают до диска.
- **Экспорт и импорт данных на флешку** — ложится к уже принятому импорту
  `.m3u` ([06](06-open-questions.md), Q9).

## 5. Отложено

**Голосовое озвучивание (Piper TTS).** Идея приятная — называть станцию
при переключении пресета. Но: в требованиях этого нет, появляется зависимость
и модель голоса на диске, а оценка «синтез короткой фразы около секунды на
3B+» ничем не подтверждена и на этой плате вызывает сомнения. Записано как
идея на потом; на конструкцию и на текущий код не влияет.

## 6. Порядок разработки

Порядок из рекомендаций **лучше того, что был в [07](07-bom-draft.md)**, и
принимается: начинать с самого рискованного узла, а не с самого приятного.

1. **Тюнер.** `rda5807.py`: частота, RSSI, SEEK в обоих диапазонах, RDS на FM.
   Делается **параллельно с проверкой эфира (Q7)** — оба вопроса про то,
   выполнимо ли вообще требование R1.1.
2. **MPD и Radio Browser.** Поиск → добавление → воспроизведение → пресеты →
   разворачивание плейлистов → проверка HLS-станций.
3. **Ввод.** Обработчики кнопок, энкодеров и тумблера на макете, через evdev.
4. **Интерфейс.** Экраны FM / INET / меню / настройка Wi-Fi.
5. **Питание и надёжность.** Защёлка выключения, overlayfs, watchdog,
   сценарий обновления.
6. **Полировка.** Скринсейвер, «звук раньше интерфейса», экспорт на флешку.

После первого шага прибор **уже играет** через штатный звуковой тракт —
значит риск «всё написано, но вместе не работает» снят с самого начала.
