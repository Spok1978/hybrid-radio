# 03. Нужен ли контроллер, и какой

## 1. Нужен ли вообще

Да, и это не вопрос выбора: без вычислителя половина требований физически
невыполнима. Вот полный список функций, которые кто-то обязан выполнять:

| Функция | Из требования |
|---------|---------------|
| Обработка кнопки MODE, арбитраж «эфир ↔ интернет» | R2 |
| Управление тюнером по I²C: частота, диапазон, SEEK, громкость, mute | R1.1–R1.5 |
| Разбор RDS-групп → извлечение PS (имя станции), RadioText | R1.4 |
| Хранение и редактирование пресетов | R1.6, R2.6 |
| Отрисовка меню, списков, частоты, названий на 5–7″ экране | R3, R4 |
| Обработка кнопок, антидребезг, длинные/короткие нажатия | R4 |
| Сканирование Wi-Fi, ввод пароля, хранение профиля сети | R2.1–R2.3 |
| HTTP(S)-запрос к каталогу станций, разбор JSON | R2.4 |
| Приём потока, разворачивание .pls/.m3u, декодирование MP3/AAC | R2.5 |
| Регулировка громкости, единая для обоих режимов | R5 |
| Хранение всего этого между включениями | R1.6, R2.3, R2.6 |

Отдельный второй контроллер (как STM32 в тестере витой пары) **здесь не нужен**:
нет ни жёсткого реального времени, ни быстрых АЦП. Тюнер сам держит ФАПЧ и
демодуляцию, кнопки — медленные. Один вычислитель делает всё.

## 2. Два реальных кандидата

### Кандидат 1 — Raspberry Pi (Pi 4 / Pi 5, как вариант Pi Zero 2 W)

| Что даёт | Подробности |
|---|---|
| Экран 5–7″ | Штатный DSI-дисплей или HDMI, драйверы «из коробки», кириллица без плясок |
| Wi-Fi | Встроенный; сканирование/подключение/хранение — штатный NetworkManager (`nmcli`), пароли шифруются системой |
| Интернет-радио | Любой поток: MP3, AAC+, Ogg/Opus, **HLS**, HTTPS. Готовые движки — MPD, mpv, VLC |
| Каталог станций | REST+JSON в три строки на Python |
| Тюнер | I²C штатный, RDA5807/Si4735 подключаются напрямую |
| Кнопки | GPIO, готовые библиотеки |
| Переиспользование | **Тот же стек, что в проекте cable-tester**: Python + NiceGUI + Chromium в киоске + systemd. Опыт и код уже есть |

Минусы, честно:

- **Загрузка 20–40 с.** Для прибора это норма, для радиоприёмника — заметный
  минус: «включил — играет» не получится. Лечится тем, что аппарат живёт
  включённым (потребление 3–7 Вт), а кнопкой глушится только звук.
- Питание 5 В / 3 А, требователен к качеству БП; при просадках — деградация SD.
- Некорректное выключение питания портит карту памяти → нужен либо
  контролируемый shutdown, либо read-only ФС.

### Кандидат 2 — ESP32-S3 (плата с 7″ RGB-панелью 800×480, либо ESP32-P4 с DSI 1024×600)

| Что даёт | Подробности |
|---|---|
| Мгновенный старт | Секунда — и играет. Поведение обычного бытового приёмника |
| Потребление | ~1–2 Вт, реально работает от аккумулятора |
| Цена | Плата «ESP32-S3 + 7″ 800×480 + touch» дешевле связки Pi + дисплей |
| Проверенная база | `schreibfaul1/ESP32-MiniWebRadio` — интернет-радио с RGB-дисплеем 800×480 и touch, поиск через Radio Browser, станции в `/stations.json` на карте (исправлено 2026-08-26, [24](24-main-build-p4.md)), форматы mp3/aac/mp4/opus/vorbis/flac |
| Надёжность | Нет файловой системы, которую можно убить выключением питания |

Минусы:

- Требования MiniWebRadio: ESP32-S3 **с PSRAM 4 МБ и больше**; экран
  обязательно с тачем.
- **HLS-потоки и часть HTTPS-стримов не потянет** — крупные вещатели уходят
  туда, и такие станции просто не заиграют.
- Интерфейс пишется на C++/LVGL: экранная клавиатура для пароля Wi-Fi,
  кириллические шрифты, списки — всё вручную. На Pi это готовое.
- Отладка и доработка заметно медленнее, чем на Python.

## 3. Что предлагаю

**Raspberry Pi.** Обоснование по пунктам:

1. **Экран 5–7″ с меню — это главный драйвер выбора.** На Pi он бесплатен
   (браузер/Qt, готовые шрифты, готовые виджеты списков), на ESP32 это
   основной объём работы.
2. **Ввод пароля Wi-Fi и работа с сетями** на Pi — вызов `nmcli`, на ESP32 —
   отдельная подсистема.
3. **Любые потоки играют.** Не хочется, чтобы половина найденных станций
   не открывалась из-за формата.
4. **Стек уже освоен** на cable-tester: Python + NiceGUI + Chromium-киоск +
   systemd-автозапуск. Это экономит больше, чем цена платы.
5. Открывается путь к варианту C из [02](02-fm-frontend.md) — RTL-SDR
   и единый звуковой тракт.

**Если приоритет — «включил и сразу играет, мало ест, дёшево»** — тогда
ESP32-S3 + MiniWebRadio как база. Это осознанный размен: платим временем
разработки интерфейса и частью станций.

### Решение от 2026-08-17

Платформа — **Raspberry Pi**, ESP32 отклонён. Дополнительное требование:
плата поменьше и подешевле, «не ставить большую плату под простую задачу».

Это меняет одну важную вещь по сравнению с cable-tester: на платах с 512 МБ
ОЗУ (3A+, Zero 2 W) **браузерный киоск не используем** — интерфейс пишем на
PyQt5 или pygame поверх KMS, а воспроизведение отдаём MPD/mpv в фоне.

Выбор конкретной платы и разбор стоимости — [08-cost-and-board-choice.md](08-cost-and-board-choice.md),
решение фиксируется в [06-open-questions.md](06-open-questions.md), вопрос Q3.

## 4. Роль кнопки MODE

Кнопка **не коммутирует ничего сама по себе**. Она заводится на вход GPIO
контроллера:

```
   +3,3 В ── подтяжка ──┬── GPIO (вход)
                        │
                    кнопка MODE
                        │
                       GND
```

Режим — это программное состояние прибора, а не положение органа на панели.
Кнопка лишь просит его сменить: контроллер глушит один источник, поднимает
другой, перерисовывает экран и запоминает выбор. Ровно тот же переход делают
пресет другого типа и пункт меню.

Тумблер, стоявший здесь до 2026-08-25, отклонён: он задаёт положение, а
пресеты и меню меняют режим мимо него — и подпись на панели начинает врать.
Разбор — [22](22-mode-switching.md).
