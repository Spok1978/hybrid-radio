## 1. Берём в зависимость

### 1.1. ESP-ADF — приём потока и декодирование

**Главная находка.** Официальный аудиофреймворк Espressif **поддерживает
ESP32-P4**. Дословно из README репозитория `espressif/esp-adf`, прочитано
2026-08-26:

> ESP-ADF ... is the official Advanced Development Framework for the ESP32,
> ESP32-S2, ESP32-C3, ESP32-C6, ESP32-C5, ESP32-S3, and **ESP32-P4** SoCs.

Это закрывает открытый пункт 4 из [26](26-firmware-spec.md), §11 в пользу ADF,
а не сторонней библиотеки: своё приложение пишем мы, а весь тракт «HTTP →
декодер → I²S» берём готовым и поддерживаемым производителем чипа.

Что даёт:

| | |
|---|---|
| Форматы | MP3, AAC, FLAC, WAV, OGG, OPUS, AMR, TS, плюс EQ, Downmixer, Sonic, ALC |
| Источники | HTTP, **HLS**, SPIFFS, SD-карта, A2DP, HFP |
| Сценарии | в списке применений **прямо назван Internet Radio** |

**Примеры, которые ближе всего к нашей задаче** (ветка `release/v2.x`,
каталог `examples/player/`):

| Пример | Чем полезен |
|---|---|
| `pipeline_http_mp3` | простейшее интернет-радио: HTTP-поток → декодер → выход |
| `pipeline_http_select_decoder` | **самый нужный:** выбор декодера по типу потока. Станции приходят в разных кодеках, угадывать нельзя |
| `pipeline_living_stream` | живой поток, поведение при обрывах |

**Грабли, заложенные в конструкцию ADF:**

1. **Ветка имеет значение.** В README предупреждение: начиная с v2.8
   обновления идут только в `release/v2.x`, и **master с ней несовместим**.
   Берём `release/v2.x`.
2. **ADF патчит ESP-IDF.** В корне репозитория есть каталог `idf_patches`,
   а сам ESP-IDF подключён подмодулем с закреплённой версией (на 2026-08-26 —
   v5.5.3). Это означает, что версию IDF выбираем не мы, а ADF. При
   обновлении одного придётся двигать другое.
3. **Версия IDF под P4 ограничена.** В истории коммитов есть
   `fix(ci): Skip idf v5.4.3 for p4` — то есть не любая 5.x под P4 годится.
   Перед началом сверить с таблицей поддерживаемых версий в README.

**Не проверено:** работает ли ADF на P4 **вместе с** Wi-Fi через сопроцессор
(§1.4). ADF писался под чипы с собственным радио, и стык с `esp_wifi_remote`
надо подтвердить на первом же прототипе, до того как на ADF будет построено
что-то большое.

### 1.2. MIPI DSI: чем поднимается панель

Читано в документации ESP-IDF по ESP32-P4, раздел `lcd/dsi_lcd`, 2026-08-26.
Заголовок — `esp_lcd_mipi_dsi.h` из компонента `esp_lcd`.

Порядок подъёма:

| Шаг | Вызов | Что задаётся |
|---|---|---|
| 1 | `esp_lcd_new_dsi_bus()` | `esp_lcd_dsi_bus_config_t`: `bus_id`, `num_data_lanes`, `lane_bit_rate_mbps` |
| 2 | `esp_lcd_new_panel_io_dbi()` | `esp_lcd_dbi_io_config_t`: `virtual_channel`, `lcd_cmd_bits`, `lcd_param_bits` — канал команд к контроллеру панели |
| 3 | драйвер контроллера панели | по образцу `esp_lcd_new_panel_ili9881c()`; **для нашей панели готов** — `waveshare/esp_lcd_hx8394`, §1.4 |
| 4 | `esp_lcd_panel_reset()`, `esp_lcd_panel_init()`, `esp_lcd_panel_disp_on_off()` | инициализация |
| 5 | `esp_lcd_new_panel_dpi()` | `esp_lcd_dpi_panel_config_t`: `dpi_clock_freq_mhz`, `in_color_format`, `out_color_format`, `num_fbs`, `video_timing` |

~~Отсюда прямо следует, какие именно параметры надо снять с платы.~~
**Снято 2026-08-26:** снимать не нужно, всё перечисленное приходит из BSP
платы и драйвера панели (§1.4). Раздел оставлен потому, что понимать, из чего
складывается подъём DSI, полезно и при работе с готовым BSP — особенно когда
что-то не заводится.

Полезные детали:

- `num_fbs` — число кадровых буферов, **по умолчанию один**. Для плавного
  интерфейса нужно больше; адреса берутся через
  `esp_lcd_dpi_panel_get_frame_buffer()`.
- `esp_lcd_dpi_panel_enable_dma2d()` — аппаратное копирование кадра.
- **`esp_lcd_dpi_panel_register_hooks()`** — точка, куда вешаются собственные
  операции над кадром, документация прямо называет поворот и масштабирование.
  Это и есть место стыковки с PPA (§1.3).

### 1.3. PPA — поворот кадра железом

Панель книжная, интерфейс альбомный ([26](26-firmware-spec.md), §2.1).
Поворот делает PPA — Pixel Processing Accelerator, заголовок `driver/ppa.h`:

- операции: SRM (scale-rotate-mirror), blend, fill;
- углы поворота 0/90/180/270 против часовой, `ppa_srm_rotation_angle_t`;
- функции: `ppa_register_client()`, `ppa_do_scale_rotate_mirror()`,
  `ppa_do_blend()`, `ppa_do_fill()`.

**Оговорка из документации:** движок SRM использует билинейное
масштабирование, что «может давать хроматические искажения и потерю
контраста на краях» при масштабировании. Нам нужен чистый поворот на 90°
без изменения масштаба, так что это, вероятно, не касается — но проверить
на первом же выводе картинки.

### 1.4. BSP платы и драйвер панели — из реестра компонентов

Проверено 2026-08-26 на `components.espressif.com`. Оба существуют, оба
заявлены под цель `esp32p4`:

| Компонент | Версия | Что даёт |
|---|---|---|
| `waveshare/esp32_p4_wifi6_touch_lcd_5` | 1.0.4 | BSP платы; инициализация HX8394 (с ключом `ESP_LCD_HX8394_SKIP_I2C_INIT`), подсветка через `bsp_display_brightness_init()`, `bsp_display_backlight_on/off()`, `bsp_display_brightness_set(0–100)` |
| `waveshare/esp_lcd_hx8394` | 2.1.0 | драйвер контроллера по MIPI-DSI; `HX8394_PANEL_BUS_DSI_2CH_CONFIG()` — две линии; «MIPI-DSI interface only supports ESP-IDF v5.3 and above» |

Это закрывает вопрос Q12: **дисплейный порт писать не нужно**, параметры
панели не снимаются с железа. Поворот включается опцией
`CONFIG_LVGL_PORT_ENABLE_PPA` в порте LVGL от Espressif.

**Что проверить при первой сборке:** в примере драйвера фигурирует
`HX8394_1024_600_PANEL_30HZ_DPI_CONFIG` — конфигурация под 1024×600,
не под нашу панель 720×1280. Тайминги должны браться из BSP платы,
а не из этого макроса.

**Ещё оттуда же:** для интерфейса есть **ESP-Brookesia** — Android-подобный
UI-фреймворк Espressif поверх LVGL; в примерах платы присутствует
`esp_brookesia_phone` именно на этом железе. Стилизацию Material с нуля
рисовать не обязательно.

### 1.5. Установка инструментария: обойти скрипт ADF

**[добавлено 2026-08-27, проверено на практике]** У ESP-ADF есть свой
`install.ps1`, и **пользоваться им не надо** — в нём два изъяна:

1. Он **не передаёт дальше аргумент цели**. Команда `./install.ps1 esp32p4`
   проглотит аргумент и поставит инструменты **подо все чипы сразу** —
   это лишние гигабайты.
2. Строка `[IO.Path]::Combine($IDF_PATH, "install.ps1")` использует
   переменную `$IDF_PATH`, которая нигде не задана, вместо `$env:IDF_PATH`,
   которую скрипт сам же выставил строкой выше. Работает только по
   случайности, из-за `Push-Location`.

**Как надо.** Вызывать скрипт ESP-IDF напрямую, указав цель:

```
$env:IDF_PATH = "<путь>\esp-adf\esp-idf"
Set-Location $env:IDF_PATH
& ".\install.ps1" esp32p4
```

Установка под одну цель заняла **3,4 ГБ** в `%USERPROFILE%\.espressif`
и завершилась за несколько минут. Само дерево `esp-adf` со всеми
подмодулями — ещё около 2 ГБ.

**Ещё одна практическая деталь:** клонирование с `--recursive` **не
подтянуло подмодуль `esp-idf`** (он самый большой). Остальные два
подмодуля ADF пришли нормально. Лечится отдельной командой:
`git submodule update --init --recursive esp-idf`.

### 1.7. Wi-Fi через сопроцессор: esp_wifi_remote и esp-hosted

У ESP32-P4 нет своего радио; на плате его обслуживает ESP32-C6.

**[из поисковой выдачи, требует проверки по официальной документации]**

| Что | Значение |
|---|---|
| Транспорт P4 ↔ C6 | SDIO, 4-битный режим, 40 МГц |
| Прошивка сопроцессора | `esp-hosted-mcu` slave firmware, живёт в отдельном разделе `slave_fw`, прошивается один раз перед первым использованием |
| Ключ Kconfig | `CONFIG_ESP_WIFI_REMOTE_LIBRARY_HOSTED=y` — **вместо** `ESP_WIFI_ENABLED`. **Подтверждено 2026-08-27** по официальному набору ADF `sdkconfig.defaults.esp32p4`, рядом стоит `CONFIG_SLAVE_IDF_TARGET_ESP32C6=y` |

**Порядок инициализации строгий** — esp-hosted поднимается раньше всего,
что трогает сетевой стек:

```
esp_hosted_init();
esp_hosted_connect_to_slave();
nvs_flash_init();
esp_netif_init();
esp_event_loop_create_default();
esp_wifi_init();
```

**Грабли, о которых стоит знать заранее.** В выдаче встретился отдельный
проект, посвящённый обновлению прошивки C6 на плате CrowPanel с P4: он
описывает **баг с отваливающимся Wi-Fi**, лечащийся переходом esp_hosted
с v2.3.0 на v2.9.7, причём обновление делается по SDIO, без пайки. Отсюда
практический вывод: **плата приезжает с той версией slave-прошивки, какую
залил производитель, и она может быть старой.** Если Wi-Fi будет
отваливаться — смотреть сюда прежде, чем искать ошибку у себя.

> **Оговорка от 2026-08-27.** Всё в этом разделе, кроме таблицы версий
> в [26](26-firmware-spec.md), §2.4, взято из сторонних репозиториев —
> в том числе про **другую плату**. Документация нашей платы прямо
> предупреждает: транспортные выводы P4 ↔ C6 у неё свои, и переносить их
> с чужой платы нельзя. Номера версий v2.3.0 и v2.9.7 относятся к CrowPanel;
> для нашей платы ориентироваться на таблицу в §2.4, а заводской образ C6
> считать неизвестным, пока не прочитан.

Проверить на нашей плате: какая версия esp-hosted залита в C6 и как её
обновить.

### 2.1. esp-bsp / `m5stack_tab5` — ближайший аналог нашей платы

> **Исправление от 2026-08-26.** Ниже было написано, что «для Waveshare BSP
> нет». Это неверно: я смотрела репозиторий `espressif/esp-bsp`, где плат
> Waveshare действительно нет, и распространила вывод шире, чем он верен.
> **Waveshare публикует свой BSP в ESP Component Registry, под собственным
> пространством имён** — см. §1.5. Tab5 остаётся полезным референсом, но
> необходимость в нём резко упала.

Официальный BSP Espressif. Прочитано 2026-08-26. Ближайший по железу
из тех, что публикует сама Espressif:

| | M5Stack Tab5 | Наша плата |
|---|---|---|
| SoC | ESP32-P4, 16 МБ флеш, **32 МБ PSRAM** | ESP32-P4 |
| Wi-Fi | ESP32-C6-MINI-1U | ESP32-C6 |
| Экран | **5″ 1280×720 IPS, MIPI-DSI** | 5″ 720×1280 MIPI-DSI |
| Контроллер панели | ST7123 | ожидается HX8394 |
| Тач | **GT911** по I²C | не известен |
| Кодек | ES8388 + ES7210 | ES8311 |
| Карта | microSD | microSD (TF) |

Что оттуда берём глазами **после появления своего BSP**: не подъём панели —
он у нас теперь готовый, — а то, как в живом проекте связаны BSP, LVGL и
приложение, и как обходятся с картой. Полезно при разборе, если своё не
заводится: есть с чем сравнить рабочий пример на том же чипе.

**Любопытная деталь:** в описании Tab5 разрешение указано как **1280×720**,
хотя панели этого класса физически книжные. Возможно, поворот у них уже
решён — посмотреть, как именно, до того как писать своё.

Рядом в том же репозитории: `esp32_p4_function_ev_board` (плата Espressif,
7″ 1024×600 DSI — та самая, что стояла в первом черновике ТЗ) и
`esp32_p4_eye`. Оба — дополнительные образцы работы с DSI на P4.

## 3. Список граблей — то, ради чего документ и заведён

Проверять при возникновении вопроса, прежде чем искать ошибку у себя.

| Симптом | Куда смотреть |
|---|---|
| Wi-Fi поднимается и отваливается | версия esp-hosted в C6, §1.6 |
| Сеть не инициализируется вообще | нарушен строгий порядок вызовов, §1.6 |
| Версии host и slave разъехались | таблица совместимости по веткам IDF — [26](26-firmware-spec.md), §2.4 |
| Сеть не работает при том, что всё верно | в проекте остался компонент `esp-extconn` — он несовместим с esp_hosted, удалить |
| Не собирается под P4 при свежем IDF | ревизия кристалла ниже 3.1; нужны особые настройки SDK (`CONFIG_ESP32P4_SELECTS_REV_LESS_V3`) |
| Плата ведёт себя странно или падает при работе с PSRAM | скорость PSRAM выставлена под чужую ревизию: 250 МГц допустимы только на rev3.x, на rev1.x нужно 200 — [26](26-firmware-spec.md), §11, п. 8 |
| Поворот тормозит, интерфейс дёргается | полноэкранные draw-буферы LVGL; PPA делит пропускную способность PSRAM с периферией — делать буферы частичными |
| Не собирается после обновления IDF | ADF закрепляет версию IDF подмодулем и патчит его, §1.1 |
| Странности после `git pull` в ADF | перепутаны ветки master и `release/v2.x`, §1.1 |
| `install.ps1` у ADF ставит инструменты подо все чипы и/или падает | **огрех в самом скрипте**, см. §1.7 — вызывать скрипт ESP-IDF напрямую |
| Подмодуль `esp-idf` пуст после клонирования с `--recursive` | бывает: он самый большой и отваливается. Лечится `git submodule update --init --recursive esp-idf` |
| `Failed to resolve component 'esp-adf-libs'` (или `esp-sr`) при том, что каталог существует | подмодуль числится проинициализированным, а внутри пусто. `git submodule status` показывает `+`, но файлов нет. Лечится `git submodule update --init --force components/esp-adf-libs` |
| В компонентах ADF `unknown type name 'xSemaphoreHandle'`, `portTICK_RATE_MS` undeclared | ADF `release/v2.x` пользуется именами FreeRTOS, убранными из заголовков IDF 5.5. Штатный ключ `CONFIG_FREERTOS_ENABLE_BACKWARD_COMPATIBILITY=y` возвращает их — патчить ADF не нужно |
| Сборка падает в `audio_board/lyrat_v4_3/` на `TOUCH_PAD_NUM9 undeclared` | плата в Kconfig ADF не выбрана, взялась первая по списку — LyraT на ESP32. `audio_board` компилируется всегда, его тянет `audio_stream`. Выбрать `CONFIG_ESP32_P4_FUNCTION_EV_BOARD=y`: он нужен лишь чтобы компонент собрался, звуковой тракт мы его не зовём |
| Модуль добавлен, собралось, а размер образа не изменился | никто не вызывает точку входа модуля — компоновщик выбросил его целиком. Проверять по `.bin binary size`, а не по факту успешной сборки |
| Панель молчит или сыплет мусором | тайминги и число линий DSI, §1.2 |
| Картинка есть, но рвётся при перерисовке | `num_fbs` по умолчанию равен единице, §1.2 |
| Артефакты по краям после поворота | билинейная интерполяция SRM, §1.3 |
| Поток играет не у всех станций | нужен выбор декодера по типу, а не фиксированный MP3, §1.1 |
| Файл настроек побился при снятии питания | гарантии FATFS не установлены — вопрос Q14 |
| Названия станций ломают файл | санитизация кавычек, [25](25-station-storage.md), §10 |

## 4. Что подтвердить до начала кода

1. **ADF + esp_wifi_remote на P4 работают вместе** — собрать
   `pipeline_http_mp3` под нашу плату и получить звук. Это единственная

   `esp_wifi`, то есть ADF видит обычный Wi-Fi. Два условия — убрать из

2. Какая версия esp-hosted залита в C6 нашей платы и как обновляется.
3. ~~Какую версию ESP-IDF требует текущая `release/v2.x` ADF под P4~~ —

   Пересечение с требованием драйвера панели (≥ 5.3) даёт **5.3…5.5**,

4. ~~Как решён поворот в `m5stack_tab5`~~ — **закрыто:** поворот включается

## 5. Что можно делать без платы

Проверено 2026-08-26. Эмуляторы закрывают логику и интерфейс, но **не
закрывают ни один из рискованных узлов**: панели DSI, тюнера, кодека
и Wi-Fi через сопроцессор в них нет.

| Инструмент | Что даёт | Чего не даёт |
|---|---|---|
| **LVGL PC simulator** | весь интерфейс на обычном ПК, мышь вместо пальца | только интерфейс, никакой периферии |
| **ESP-IDF, цель `linux`** | логика, автомат состояний, разбор файлов, юнит-тесты | драйверы только замоканы |
| **Wokwi** | ESP32-P4 в бете; Wi-Fi, I²C, GPIO, UART, SPI, таймеры | **I²S не симулируется** — звука нет; карты и DSI тоже нет |
| **QEMU** | виртуальный фреймбуфер, отладка через GDB | под P4, судя по всему, не поддержан |

### 5.1. Интерфейс — LVGL на ПК

Самое ценное. LVGL штатно собирается и работает на настольном компьютере,
и код потом переносится на прибор без переделки. Официальный порт под
Windows — `lvgl/lv_port_pc_visual_studio`: использует встроенные windows-драйверы
LVGL, открывает окно с отрисованным интерфейсом, мышь работает вместо
касания. Зависимостей кроме Win32 API, C Runtime и C++ STL нет. Есть вариант
на CMake — `lv_port_pc_visual_studio_cmake`, и вариант на SDL под Eclipse —
`lv_port_pc_eclipse`.

Что через него делается **до прихода платы**: все экраны, структура меню,
русская экранная клавиатура с переключением раскладок, списки станций,
шкала диапазона, ждущий режим с часами, вся отработка Material-стиля
и читаемости крупным шрифтом. Это большой кусок работы по
[26](26-firmware-spec.md), §5 и §7, и он не требует железа вообще.

Чего он не покажет: скорость отрисовки на реальном чипе и поведение
поворота через PPA.

### 5.2. Логика — цель `linux` в ESP-IDF

```
idf.py --preview set-target linux
idf.py build
idf.py monitor
```

Два способа: моки на CMock — код в полной изоляции; и симулятор FreeRTOS
поверх POSIX — каждая задача становится потоком ОС, поддержка компонентов
шире. Полностью поддержаны `freertos`, `esp_event`, `esp_partition`;
`driver`, `spi_flash` и `tcp_transport` — только частичные моки.

Что здесь отлаживается: конечный автомат режимов, модель громкости
с поправкой, банк пресетов, чтение и запись `/ipradio.json`, разбор ответов
Radio Browser.

Ограничения, о которых надо помнить: **вытеснение кооперативное** — задача,
крутящаяся в цикле без вызова FreeRTOS API, не будет вытеснена никогда;
гранулярность таймингов равна такту; блокирующие примитивы FreeRTOS нельзя
звать из чужих потоков. То есть гонки, найденные здесь, реальны, а не
найденные — ничего не доказывают.

### 5.3. Wokwi — чип целиком, но без звука

Wokwi симулирует ESP32-P4, помечен как **beta**. Симулируются Wi-Fi, I²C
(только master), GPIO с прерываниями, UART, SPI, ADC, таймеры, watchdog.
**Не симулируются: I²S**, Bluetooth, USB, MCPWM.

Отсутствие I²S для нас решающее: именно туда идёт звук. То есть проверить
на Wokwi звуковой тракт ADF, ради которого эмулятор был бы интереснее
всего, **нельзя**.

### 5.4. Что это даёт по проверкам из §4

Проверка 1 («ADF и Wi-Fi через сопроцессор работают вместе») распадается
на две части:

- **собирается ли** связка ADF `release/v2.x` + `esp_wifi_remote` под P4 —
  проверяется **без платы**, одной сборкой;
- **играет ли звук** — только на железе, ни один эмулятор I²S не даёт.

Проверки 3 и 4 (версия IDF под ADF, как решён поворот в Tab5) — тоже
без платы, это чтение и сборка.

### 5.5. Чего не хватает на машине

На 2026-08-26 ESP-IDF не установлен: `idf.py` в PATH нет, каталогов
`C:\Espressif` и `~/.espressif` нет. Для §6.1 дополнительно нужен
Visual Studio.
