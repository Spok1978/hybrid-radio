# Правка ESP-IDF: зависание PPA при повороте экрана

**Дата:** 2026-09-05
**Файл:** `$IDF_PATH/components/esp_driver_ppa/src/ppa_srm.c`
**Копия оригинала:** рядом, `ppa_srm.c.orig-before-ipradio`

Эта правка лежит **вне репозитория** — в дереве ESP-IDF. При обновлении
или переустановке ESP-IDF она пропадёт, и зависание вернётся. Отсюда
этот файл: чтобы было понятно, что именно и зачем менялось.

## Что было

Прибор намертво замирал через несколько секунд после начала
воспроизведения. Экран переставал обновляться и не отзывался на
касания, кнопки не работали. В журнале — одно и то же раз в полсекунды:

```
E esp_lvgl:adapter: esp_lv_adapter_lock(751): Failed to acquire LVGL lock
```

Прибор при этом был жив: главная задача продолжала печатать пульс,
память не кончалась, сторож не срабатывал.

## Как искали

Перепись всех задач (`uxTaskGetSystemState`) показала, что **ни одна
задача не выполняется — стоят все**. То есть ни голодания процессора,
ни зацикливания. Период сбоя блокировки — ровно 550 мс, а это цикл
нашей задачи интерфейса (ожидание 500 мс плюс шаг 50 мс). Значит,
замок держит задача `lvgl`: она заходит в отрисовку, встаёт внутри
и не выходит. Косвенно подтверждается остатком её стека — он замирал
на 1568 байт вместо обычных 2088, то есть задача припаркована глубоко
в вызове.

Проверено и отброшено по очереди:

| Версия | Как проверяли | Итог |
|---|---|---|
| Нехватка памяти | замер на старте конвейера | 38,7 КБ свободно — не она |
| Столкновение выводов | сверка I2S 46–48 с картой платы | не пересекаются |
| Драка за ядро | LVGL на ядро 0, i2s на ядро 1 | не помогло |
| Стеки задач ADF в PSRAM | вернули стек i2s во внутреннюю | не помогло |
| Виноват вывод звука | собрали конвейер без элемента i2s | зависает так же |

## Настоящая причина

Известная аппаратная ошибка PPA на ESP32-P4, **DIG-734**. Проявляется
только при сочетании: ESP32-P4, режим `TEAR_AVOID_MODE_TRIPLE_PARTIAL`
и поворот экрана на 90 или 270 градусов. У нас ровно оно.

В `ppa_srm.c` обход этой ошибки включался по эвристике, считающей
размеры блока. Эвристика иногда решает обход не включать — и PPA
встаёт. Поворот не завершается, задача `lvgl` замирает внутри
отрисовки с замком LVGL в руках, экран умирает. Зависит от размеров
перерисовываемой области — поэтому вылезало не сразу, а когда экран
начинал обновляться часто.

Описано у Espressif:
<https://docs.espressif.com/projects/esp-iot-solution/en/latest/display/tools/esp_lvgl_adapter.html>

Патч приложен к самому компоненту:
`managed_components/espressif__esp_lvgl_adapter/0001-bugfix-ppa-Temporary-fix-for-the-PPA-hang-issue.patch`

## Что сделано

Дословно патч на ESP-IDF 5.5.3 **не ложится**: в нашей версии
`color_hal_pixel_format_get_bit_depth`, а в патче
`color_hal_pixel_format_fourcc_get_bit_depth`, из-за чего расходится
контекст. Правка внесена вручную, смысл тот же: весь блок эвристики
удалён, обход включается всегда.

Было:

```c
// Hardware bug workaround (DIG-734)
uint32_t w_out = ...;
...
bool bypass_mb_order = false;
if (((w_out > w_divisor) || (srm_trans_desc->in.block_h > h_mb)) &&
        ((w_left * h_left * out_pixel_depth) < dma2d_fifo_depth_bits)) {
    bypass_mb_order = true;
}
ppa_ll_srm_bypass_mb_order(platform->hal.dev, bypass_mb_order);
```

Стало:

```c
ppa_ll_srm_bypass_mb_order(platform->hal.dev, true);
```

## Как проверить, что правка на месте

```bash
grep -n "bypass_mb_order" $IDF_PATH/components/esp_driver_ppa/src/ppa_srm.c
```

Должна быть ровно одна строка, с `true`. Если строк снова стало
несколько и рядом появился комментарий про DIG-734 — правка потеряна,
надо внести заново.

## Чем ещё можно обойтись

Если правка в ESP-IDF почему-то неприемлема, ошибка обходится сменой
режима: она проявляется только на `TRIPLE_PARTIAL` вместе с поворотом.
Любой другой режим из `esp_lv_adapter_display.h` её не задевает. Цена —
либо больше памяти под полные кадровые буферы, либо разрывы кадра.
